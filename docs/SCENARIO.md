# 개발 시나리오 구조 (v0.2, 2026-11-27)

> 목적이 기능을 결정하고, 기능이 기술을 결정하며, 검증이 다음 판단을 결정한다.
> 바이브 코딩의 역량은 컴퓨터 과학에 대한 이해에서 나온다.

## 1. 구간 = 목적 하나 + 그 목적의 기능

기술 이름이나 코드 파일을 구간·장의 기준으로 쓰지 않는다. 독자는 기술을 공부하려고 개발하지 않고, 필요한 기능을 만들면서 기술을 겪는다.

| 구간 항목 | 내용 | CS Studio 에서 보이는 곳 | 남기는 방법 |
|---|---|---|---|
| 목적 | 이 구간에서 이루려는 것 | 목적 칸(위) | `ctx goal` |
| 필요한 기능 | 목적을 이루는 기능 | 목적 칸 — 현재 기능 | `ctx feature` |
| 성공 조건 | 무엇을 보면 목적 달성인가 | 성공 조건·검증 칸 | `ctx success` |
| 현재 시스템 상태 | 지금 구조로 되는가 | 흐름도·프로젝트 구조 | `say` |
| 해결할 문제 · 기존 방식의 한계 | 가능하면 기존 방식으로 먼저 돌려서 드러난 것 | 문제 칸 | `ctx limit / problem`, `ctx experiment --kind real` |
| 검토할 기술과 대안 | 후보와 장단점(가능하면 실제 비교) | 대안 칸 | `ctx option`, `ctx experiment --kind compare` |
| 선택한 기술과 이유 | 도입하지 않는 판단 포함 | 선택 칸 | `ctx decide --why` |
| 구현 작업 | 의미 있는 변화 하나씩(함수·모델·API·저장 방식 …) | 코드(작성 중) | Write/Edit → PRESENT |
| 시스템 구조 변화 | 구성 요소·역할·연결이 어떻게 자라는가 | 흐름도(새 상자는 파란 테두리) | `arch node / link` |
| 데이터 흐름 변화 | 입력 → 처리 → 저장 → 출력의 경로 | 파라미터 · 흐름도 강조 | run.py 계측(자동) |
| 실제 구현 화면 | 사용자가 보는 실제 화면 | 실제 구현 화면 | run.py 로 띄운 서비스 |
| 관찰할 실행 결과 | 요청·응답·함수 인자·반환·쿼리·출력 | 파라미터 · 로그 · 실행 중 코드 | run.py 계측(자동) |
| 목적 달성 검증 | 실제 요청·응답을 근거로 판정 | 검증 칸 | `ctx verify pass/fail` |

- 새 기술이 없는 구간도 정상이다. 그때 선택은 "기존 방식 유지 + 이유".
- 실패는 실제로 겪은 것(`real`)과 차이를 보여 주려는 비교(`compare`)를 나눠 남긴다. 없는 문제를 지어내지 않는다.
- 파일 존재(`VALIDATE`)는 완료 판정이 아니다. 완료 판정은 ① 쓰려던 내용이 실제로 들어갔는지(`VALIDATE content_ok`) ② 실제 요청·실행 결과 ③ 처음 목적(`verify`).

## 2. 공통 식별자 — 하나의 일을 모든 화면에 잇는 방법

| 식별자 | 무엇을 묶나 | 어디에 붙나 |
|---|---|---|
| `ctx.goal` · `ctx.feature` (G·F 번호) | "무엇을 위해" | 서버가 **모든 이벤트**에 자동으로 붙임 |
| `present` (PRESENT 이벤트 id) | 코드 한 변화의 표시 → 실행 → 검증 | CREATE_FILE / MODIFY_CODE / RUN_COMMAND 의 `data.present` |
| `trace` (T 번호) | 실행 중 요청 하나의 요청 → 함수 호출·인자 → DB·파일 → 응답 → 출력 | 계측 이벤트 전부의 `data.trace` |
| 구성 요소 id (`arch`) | 코드 파일 ↔ 흐름도 상자 | `arch node --files` 로 연결, 실행 이벤트의 파일·종류로 상자를 찾음 |
| `Q` 번호 · `explore` | 과외 질문과 그 실험 | QUESTION, 과외 중 작업의 `data.explore` |

예: 독자가 구현 화면에서 '일정 등록' 을 누르면 → `HTTP_REQUEST(T7)` 로 클라이언트·서버 상자가 강조되고 → `HTTP_BODY(T7)` 입력값 → `CALL validate(T7)` 서비스 상자와 코드 줄 강조, 인자 값 → `RETURN` 변환 결과 → `DB_QUERY(T7)`/`FILE_IO(T7)` 저장 상자 → `HTTP_RESPONSE(T7)` 응답 → 구현 화면 갱신. 모두 T7 로 묶여 파라미터·코드·로그·흐름도가 같은 순서로 재생된다.

## 3. 실제 관측과 개념 설명
- 실제 관측: 계측(run.py)·hook 이 수집한 값만. 흐름도의 초록 강조, 파라미터, 로그, 실행 중 코드.
- 개념 설명: 직접 관측하지 않는 원리(OS 스케줄링, 네트워크 계층, 가중치 전체 …). `say` 로 설명할 때 "원리 설명" 이라고 밝힌다. 관측하지 않은 값을 관측처럼 표시하지 않는다.
- 관측 범위는 교육에 필요한 만큼 정하고 그 안에서만 실제 값을 모은다.

## 4. 저자 → 독자
1. 저자가 Studio 로 실제 서비스를 처음부터 만든다(저자 모드). 기록: `events.jsonl`, `context.json`, `arch.json`.
2. 구간마다 정리: 목적·기능·문제·선택·검증, 구조 변화, 데이터 흐름, 필요했던 시각화, 독자가 해 볼 실험.
3. 재현 가능하고 교육적으로 의미 있는 순서로 정제해 독자 구간으로 만든다. 저자 로그를 그대로 재생하지 않는다.
4. 독자 모드는 그 경로를 독자 PC 에서 **실제로 다시 개발·실행**한다. 질문과 자유 탐구는 Claude 가 실시간으로.

독자 구간 파일 형식은 첫 구간들을 실제로 만든 뒤 기록에서 뽑아 정한다(아직 미정).

## 5. 서비스와 범위
여행 동선 서비스에서 시작해 요구사항·기획, 입력·처리·출력, 웹·앱, 서버·API, 데이터 저장, 지도·경로 최적화, 자료구조·알고리즘, OS·네트워크, 동시성, 아키텍처, 테스트·디버깅, 클라우드·배포, 운영, 외부 AI, 자체 AI 학습·평가·서빙, 에이전트 오케스트레이션까지. **범위이지 순서가 아니다.**

자체 AI 모델도 같다: AI 가 필요한 기능 정의 → 규칙·기존 알고리즘으로 충분한지 → 외부 모델로 성능·비용·지연·실패 측정 → 자체 모델의 역할 발견 → 데이터·토큰화·구조·텐서·학습 파라미터·손실·옵티마이저·체크포인트·평가 → 서빙 → 비교. 학습 완료가 아니라 기능·목적 달성으로 판정한다. 함수의 입력 파라미터와 모델의 학습 파라미터는 다른 개념임을 실제 상황에서 구분해 보여준다.
